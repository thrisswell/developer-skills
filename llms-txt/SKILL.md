# llms.txt Generator

Generate a single `llms.txt` file at the **root of the codebase** that gives any LLM — or developer — a complete, structured understanding of the project.

**Core principle: use tokens wisely.** Mechanical tasks (directory trees, extracting function/class names) are handled by scripts bundled with this skill. The LLM's job is understanding and explaining — not listing files or parsing syntax trees.

---

## Output Format

The generated `llms.txt` must contain these sections in order:

```
# <Project Name>

## Title
<One-line description of the codebase>

## Description
<10-line paragraph in simple, plain English explaining what the codebase is about>

Key features:
- <feature 1>
- <feature 2>
- ...

## Usage
<Who uses this and how. State whether it is a consumer app, enterprise tool, developer library,
internal service, or a combination. Describe the primary use cases and the problems it solves.>

## Tech Stack
- **Languages:** ...
- **Frameworks:** ...
- **Libraries / Packages:** ...
- **Dev Tools:** ...
- **Database / Storage:** ...
- **Other:** ...

## Directory Structure
<tree output — generated by script, not by the LLM>

## File Reference
<For every meaningful file: a short overview, then each important class/function listed with
its purpose. Group by directory.>
```

## Workflow

Follow these steps in exact order. **Do not skip the script steps** — they exist to save tokens and produce more accurate output than the LLM guessing at file names and symbol lists.

### Step 0 — Locate the codebase root

Identify the root directory of the project. Look for markers: `.git/`, `package.json`, `pyproject.toml`, `Cargo.toml`, `go.mod`, `pom.xml`, or the top-level `README`. If ambiguous, ask the user.

### Step 1 — Generate the directory tree (SCRIPT, not LLM)

Run the bundled tree generator script. This handles `.gitignore` rules, skips binary/generated directories, and produces a clean ASCII tree — no LLM tokens spent.

```bash
python3 "<skill-dir>/scripts/tree_gen.py" "<codebase-root>"
```

If `python3` is unavailable, try the Node.js version:
```bash
node "<skill-dir>/scripts/tree_gen.js" "<codebase-root>"
```

If neither Python nor Node is available, fall back to system commands:
- **macOS/Linux:** `find . -not -path '*/\.*' -not -path '*/node_modules/*' -not -path '*/__pycache__/*' | sort | head -500`
- **Windows:** `tree /F /A` from the project root

Capture the output — this goes directly into the `## Directory Structure` section.

### Step 2 — Extract symbols from code files (SCRIPT, not LLM)

Run the bundled symbol extractor. It uses Python's `ast` module for `.py` files and regex-based parsing for `.js`, `.jsx`, `.ts`, `.tsx`, `.go`, `.java`, `.rb`, `.rs` files. It outputs every class, function, and method name per file — no LLM tokens spent.

```bash
python3 "<skill-dir>/scripts/extract_symbols.py" "<codebase-root>"
```

If `python3` is unavailable, try the Node.js version:
```bash
node "<skill-dir>/scripts/extract_symbols.js" "<codebase-root>"
```

If neither Python nor Node is available, use `grep` as a fallback:
```bash
grep -rnE '^\s*(export\s+)?(async\s+)?function\s+\w+|^\s*(export\s+)?(default\s+)?class\s+\w+|^\s*def\s+\w+|^\s*class\s+\w+' --include='*.py' --include='*.js' --include='*.ts' --include='*.jsx' --include='*.tsx' "<codebase-root>"
```

Capture the output — you'll use this as a scaffold for the `## File Reference` section.

### Step 3 — Read key files for understanding (LLM task)

Now read the actual source files to understand the codebase. Prioritise in this order:

1. **README**, **CONTRIBUTING**, **ARCHITECTURE** docs — highest signal, read first.
2. **Config files** — `package.json`, `pyproject.toml`, `Cargo.toml`, `go.mod`, `Gemfile`, `pom.xml` — for tech stack and dependencies.
3. **Entry points** — `index.ts`, `main.py`, `app.py`, `main.go`, `App.tsx`, `server.ts`, etc.
4. **Core modules** — the `src/`, `lib/`, `pkg/`, `app/` directories.
5. **Routes / Controllers / Handlers** — for understanding what the app does.
6. **Models / Schemas / Types** — for understanding data structures.
7. **Config / Environment** — `.env.example`, `config/` — for deployment context.

Skip reading:
- Lock files (`package-lock.json`, `yarn.lock`, `uv.lock`, `poetry.lock`)
- Generated files (`dist/`, `build/`, `.next/`, `__pycache__/`)
- Binary assets, images, fonts
- Test fixtures and snapshot files (read test files themselves if needed for understanding)

### Step 4 — Determine tech stack (LLM task, informed by config files)

From the config files read in Step 3, compile the tech stack. Be specific:
- Don't just say "React" — say "React 18 with TypeScript".
- Don't just say "database" — say "PostgreSQL via Prisma ORM" or "MongoDB via Mongoose".
- List dev tools separately (ESLint, Prettier, Jest, Docker, etc.).

### Step 5 — Write the Title, Description, and Usage (LLM task)

Write these sections based on your understanding from Steps 3–4.

**Title:** One line. Factual. Not marketing copy.

**Description:** 10 lines of plain English. Assume the reader is a developer who has never seen this codebase. Explain what it does, not how it's built. Follow with bullet-point feature highlights.

**Usage:** Be specific about who the users are:
- **Consumer app** — end users interact with it directly (web app, mobile app, CLI tool)
- **Enterprise** — business teams, internal tooling, B2B SaaS
- **Developer library/tool** — other developers consume it as a dependency or use it in their workflow
- **Internal service** — microservice, background worker, infrastructure component
- State clearly if it's a combination. Describe the main workflows or use cases.

### Step 6 — Write the File Reference (LLM + script output)

Using the symbol list from Step 2 as a scaffold and your understanding from Step 3, write the `## File Reference` section.

**Format for each file:**

```
### `path/to/file.ext`
<1–3 sentence overview of what this file does and why it exists>

| Symbol | Type | Purpose |
|:-------|:-----|:--------|
| `ClassName` | class | <what it does> |
| `functionName` | function | <what it does> |
| `CONSTANT_NAME` | constant | <what it represents> |
```

**Rules:**
- Group files by directory. Add a one-line description of each directory before listing its files.
- Skip trivial files: `.gitignore`, `LICENSE`, lock files, empty `__init__.py`, barrel `index.ts` files that only re-export.
- For large codebases (50+ files), focus on the most important files. Add a note: *"Only key files are documented. Run the extract script for a complete symbol list."*
- Don't fabricate symbols. If the script output lists `fetchUsers`, `createUser`, `deleteUser` — those are the functions. Don't invent others.

### Step 7 — Assemble and write `llms.txt`

Combine all sections into the final `llms.txt` file and write it to the codebase root.

After writing, report:
- The path to the generated file
- Total file count and approximate line count of the codebase
- Any files or directories you skipped and why

## Token Optimisation Rules

These are not suggestions — they are hard constraints:

1. **Never use the LLM to generate a directory tree.** The script does this in zero tokens.
2. **Never use the LLM to list function names from a file.** The script extracts symbols via AST/regex.
3. **Read files selectively.** A 200-file codebase does not require reading all 200 files. Read entry points, core modules, and config. Skim the rest via the symbol list.
4. **Don't repeat the tree in the file reference.** The tree section and the file reference section serve different purposes — one shows structure, the other shows content.
5. **Batch file reads.** Read multiple related files in one pass rather than one at a time.
6. **Stop when you have enough signal.** If 10 service files follow the same pattern, read 2–3 thoroughly and note the pattern.

---

## Constraints

- **DO NOT** include secrets, API keys, tokens, passwords, or connection strings in `llms.txt` — even if they appear in `.env.example` or config files. Mention the env var name, not the value.
- **DO NOT** include the contents of lock files, compiled output, or binary files.
- **DO NOT** invent or hallucinate file names, function names, or class names. Every symbol in the output must come from the script extraction or your direct reading of the file.
- **DO NOT** write marketing copy. The description and usage sections are factual developer documentation.
- **DO** respect `.gitignore` — if a file is gitignored, it should not appear in the tree or file reference.
- **DO** note if the codebase appears incomplete, misconfigured, or has obvious issues — this is useful context for any LLM consuming the file.

## Reference Scripts

- `scripts/tree_gen.py` / `scripts/tree_gen.js` — Cross-platform directory tree generators. Respect `.gitignore`, skip binary/generated directories, output clean ASCII tree. Use the Python one preferably, but JS is provided for Node-only environments.
- `scripts/extract_symbols.py` / `scripts/extract_symbols.js` — Extracts class, function, and method names from source files. The Python version uses AST parsing for `.py` and regex for others; the JS version uses regex for all. Outputs structured text per file.
